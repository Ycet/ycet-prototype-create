# 功能四：现有 HTML 或图片原型规范化与编辑

## 目标

接管非本 Skill 生成的 HTML 或图片原型，按 Manifest 驱动的新框架体系审计、分级规范化，再执行用户要求的编辑。原有 Level 1/2/3 门禁保持不变。

开始前读取 `shared-prototype-standards.md`、`shared-editlog-rules.md` 与 `../assets/frames/manifest.json`。

## 产品端口确认门禁

本门禁优先于原型读取、审计、导入、框架选择和文件写入。每次启动功能四时，必须先向用户询问一遍：

> 当前产品原型是什么产品端口？请选择 iOS/iPhone、Android、iPad、网页/网站、桌面端/Windows/macOS 或微信小程序；若为微信小程序，请同时说明宿主设备，或明确答复“使用默认宿主”。

即使用户的初始描述、文件名或已有配置看似已经表明端口，也必须重新询问并获得明确回复。不得通过现有 HTML、图片内容、画布尺寸、系统 UI、文件名、目录名、Spec、`index.html`、旧框架、`frame-config.json` 或其他元数据自行判断、替用户确认或覆盖用户回复。用户明确回复前，不得开始读取或审计用户原型，不得决定重构等级，不得导入资源、选择或复制框架，也不得生成或修改文件。

用户明确回复后，只能按与功能一完全一致的规则从 Manifest 选择设备框架：

| 产品端口 | 设备框架 |
| --- | --- |
| iOS、iPhone | `iphone-15-pro` |
| Android | `android-pixel` |
| iPad | `ipad-pro` |
| 网页、网站 | `browser-chrome` |
| 桌面端应用、Windows、macOS | `macbook` |
| 微信小程序 | 默认 `iphone-15-pro`；用户明确指定 Android 宿主时使用 `android-pixel` |

若用户选择微信小程序但未说明宿主设备或“使用默认宿主”，继续询问并等待回复；若回复包含多个端口或含义不明确，先确认本次任务对应的唯一端口。现有原型与用户确认端口不一致时，只将差异作为后续审计证据，不得改用推断端口。

## 输入类型

| 输入 | 处理方式 |
| --- | --- |
| HTML 原型 | 产品端口确认 → 合规审计 → 建议重构等级 → 用户确认 → 规范化 → 用户编辑 |
| 图片原型 | 产品端口确认 → 导入资源 → 确认命名 → 选择端口框架 → 生成承载页面与入口 |

## HTML 审计

检查：

- 是否位于 `prototype/` 结构内；
- 是否存在独立 `pages/` 页面；
- 是否存在 `frame-config.json`；
- 项目配置、`index.html` 和 Manifest 是否一致；
- 框架文件是否存在并支持 `screen` 协议；
- 页面根画布是否匹配逻辑尺寸；
- 页面是否重复绘制系统 UI；
- 安全区域、滚动容器和产品固定导航是否合理；
- iframe 是否溢出、裁剪、留白或出现原生滚动条；
- `index.html` / 设计预览中框架 iframe 是否等于项目 `preview` 固定像素，是否被百分比或二次 scale 压扁；
- 是否存在外链内容图（如 `img[src^="http"]`）或 CSS 远程内容背景图；
- 是否存在远程图标 CDN / 远程 SVG 图标依赖；
- 是否用灰色占位或图标冒充内容图；
- 本地图片/图标相对路径是否指向存在文件；
- 本地样式、脚本、字体、`srcset`、CSS `url()` / `@import` 和模块 import 是否在迁移后仍指向存在文件；
- 是否存在 EditLog。

### 新框架配置异常

- 配置缺失：只根据门禁中用户已确认的产品端口与 Manifest 得到候选框架；`index.html`、框架文件名和 Spec 仅作为一致性审计证据，不得用于推断产品端口。
- 配置无效或与 `index.html` 冲突：列出差异，不静默覆盖。
- Manifest 或框架文件缺失：报告并停止新框架迁移。

### 旧框架

识别 `.phone-frame`、`.android-frame`、`.miniapp-frame`、`.browser-frame`、`.desktop-frame` 等旧结构。旧尺寸只用于理解当前页面，不写入新 Manifest。

## 分级重构

| 等级 | 适用情况 | 允许动作 |
| --- | --- | --- |
| Level 1 轻量接管 | 页面视觉和结构基本正常 | 迁入 `pages/`，按迁移前后的文件位置重写本地资源相对路径，根据端口按需复制框架，补齐 `frame-config.json` 与 `index.html` |
| Level 2 结构修复 | iframe 不稳定或系统 UI 重复 | 修复逻辑画布、滚动、安全区域、系统/产品 UI 边界和新框架引用 |
| Level 3 规范化重写 | 严重不合规或无法稳定迁移 | 保持内容、文案和功能表达不变，重写 HTML/CSS |

Level 3 必须先获得用户确认。

## HTML 处理流程

1. 执行产品端口确认门禁并等待用户明确回复。
2. 完成审计并展示证据。
3. 建议最低必要重构等级。
4. 用户确认等级；Level 3 未确认不得继续。
5. 根据已确认产品端口从 Manifest 选择设备框架，按需复制并生成项目配置快照。
6. 规范化页面与入口，不改变未授权内容；移动 HTML 前以原文件 URL 为基准解析本地 `src`、`srcset`、`href`、CSS `url()` / `@import` 和模块 import，移动后按新文件位置重写为项目内相对路径并逐项验证存在；同时将外链内容图下载到 `assets/images/`、远程图标下载到 `assets/icons/`。无法下载时按近似图顶替/语义阶梯处理，仍失败则暂停报告。
7. 执行用户明确要求的编辑。
8. 分别记录“规范化重构”和“用户要求的编辑”；资源本地化与降级一并记入 EditLog。

## 图片原型流程

整页图片原型不套用内容图图库语义匹配阶梯；文件保持本流程落盘约定，须在 `prototype/` 内离线可打开。页面内插图类内容图仍遵守 `shared-prototype-standards.md`「图片与图标」。

1. 执行产品端口确认门禁并等待用户明确回复。
2. 将原始整页图片保存到 `prototype/pages/source-images/`，文件名使用清晰英文名；该目录是功能四图片原型的兼容资源目录，不作为 `screen` 直接目标。
3. 提醒用户改为清晰英文文件名，并等待确认。
4. 根据已确认产品端口与宿主设备，从 Manifest 选择设备框架。
5. 按需复制框架并生成 `frame-config.json`。
6. 在 `prototype/pages/` 生成同语义英文名的独立承载 HTML，在页面中使用 `source-images/<image-file>` 引用原图，并生成 `index.html`。
7. 图片完整展示，不被裁剪且无无意义留白；长图在框架内部纵向滚动。
8. 记录图片导入、承载页面、框架和配置写入。

## 迁移规则

- 框架负责系统 UI，页面只保留产品 UI。
- 新入口使用 `data-ycet-frame-id` 与 `?screen=pages/<file>.html`。
- 迁入 `pages/` 的 HTML 必须重写所有受目录层级变化影响的本地资源引用；不得只修图片和图标。
- 页面根画布和安全区域读取项目配置。
- 只复制选中框架，所有路径保持项目内相对。
- 不为了迁移顺手重写业务文案、视觉风格或页面流程。
- 原型已使用新框架且配置有效时，不重复迁移。

## 完成标准

- HTML 或图片原型已纳入标准 `prototype/` 结构。
- 用户已明确回复产品端口；所选框架与功能一的 Manifest 端口映射一致，未使用原型内容或既有配置替用户判断。
- 项目配置、框架、入口和页面一致。
- 系统 UI 无重复，页面在框架中完整显示。
- 外链内容图与远程图标已本地化，或已记录用户明确例外。
- 无灰色占位/图标冒充内容图；断网后资源仍可显示。
- Level 1/2/3 变更未越权。
- 用户要求的编辑已完成。
- EditLog 分别记录迁移与编辑。
- 本地 HTML、静态服务器和目录迁移测试通过。
