# 目标

约束后续 Agent 按已批准 Spec 完成 `ycet-prototype-create` 优化：将不完整需求流程切换到 `brainstorming-solo`，增加 UI Skill 混合发现与单选流程，建立 Manifest 驱动的设备框架库，并让功能一、功能三、功能四及共享规范使用同一框架体系。

本计划只规定执行边界、依赖顺序、验收和风险控制，不是逐文件或逐函数的编码剧本。

# 必须遵守的边界

1. 以已批准 Spec 为唯一需求依据；发现冲突时停止并请用户确认，不自行扩大范围。
2. 实施前读取项目 README、当前 Skill 入口、受影响功能文档、共享规范、框架 README 与当前 Git 状态。
3. 保留用户已有未提交、未跟踪和删除状态；只修改能够追溯到本次 Spec 的内容。
4. 不完整需求使用 `brainstorming-solo`；完整 PRD 继续使用 `grill-me`。
5. UI Skill 采用会话清单加标准本地目录的混合发现，展示全部有效 UI 相关 Skill，但一次只允许一个主 Skill。
6. 框架库中的 `manifest.json` 是设备规格唯一真源；框架 HTML 与 README 必须同步。
7. 生成项目只复制当前端口使用的框架，并写入 `prototype/assets/frames/frame-config.json` 快照。
8. 框架负责系统 UI，页面负责产品 UI；不得重复绘制状态栏、Home Indicator 或 Android 系统导航栏。
9. 功能三、功能四只做新框架兼容，不改变既有业务流程、确认门禁、命名规则和重构等级。
10. 新原型使用框架 ID、Manifest 和项目配置；旧 CSS 类仅用于已有原型兼容。
11. 双层 iframe 必须使用已确认的消息协议、页面白名单和来源校验。
12. 关键 HTML/CSS/JS 添加中文注释。
13. 任何原型 HTML、预览、项目框架配置和项目内框架文件变更均按 Spec 更新 EditLog 规则。

# 明确不要做的事

- 不修改功能二精准编辑的业务逻辑。
- 不自动安装、下载、删除或升级 UI Skill。
- 不将 UI Skill 示例写成固定白名单。
- 不允许多个主 UI Skill 同时指导设计方向。
- 不未经用户明确要求打开外部网页。
- 不把 Skill 源目录绝对路径写入生成的 `prototype/`。
- 不在 Manifest 无效时静默回退旧尺寸。
- 不把未经测量的安全区域数值写成已验证事实。
- 不把旧原型尺寸写回新 Manifest。
- 不为了适配新框架重设计功能三或功能四的业务流程。
- 不恢复、删除或覆盖与本次任务无关的工作区文件。
- 不使用 `git reset --hard`、`git checkout --` 等破坏性方式清理工作区。
- 不自动执行 Git add、commit、push、发布或全局安装。

# 建议执行顺序

1. 执行工作区预检：确认 README、目录结构、受影响文件、当前 Git 状态和用户已有改动边界。
2. 先建立框架数据真源：将五个框架纳入 Skill 资产目录，设计并校验 `manifest.json`，同步框架 README。
3. 调整框架 HTML：统一逻辑画布、预览缩放、安全区域、系统 UI、`?screen=` 加载和消息中继协议。
4. 更新共享原型规范和 EditLog 规则，使目录、尺寸、职责边界、预览页、项目配置和日志范围与 Manifest 一致。
5. 更新总入口与功能一：替换需求完善 Skill，增加 UI Skill 混合发现、单选、特殊链接、无 Skill 分支、首页预览和按需复制规则。
6. 更新功能三：优先读取项目框架配置，使用双层 iframe 通信，同时保留旧框架兼容模式。
7. 更新功能四：按 Manifest 审计和迁移新旧原型，保留 Level 1/2/3 业务门禁。
8. 同步 README、Agent 元数据和仍处于项目范围内的相关评估规则；若评估文件处于用户删除状态，先确认意图，不擅自恢复。
9. 运行文档、JSON、路径和静态结构检查，修复 Manifest、框架源码、README 与功能文档之间的不一致。
10. 使用代表性页面验证设计方向页、静态入口、交互 Demo、旧原型兼容和 EditLog。
11. 分别通过本地 HTML 与本地静态服务器验证，再复制整个 `prototype/` 到新目录进行可移植性复测。
12. 最后检查 Git diff，确认所有改动均可追溯到批准 Spec，且没有覆盖用户无关修改。

# 关键依赖与前置条件

- 已批准 Spec：`../specs/2026-07-12-ycet-prototype-create-ui-skill-frame-workflow-spec.md`。
- 当前五个框架资产及其 README 可读取。
- 实施环境可读取当前会话 Skill 清单或至少一个标准本地 Skill 目录。
- 可使用浏览器或等效本地网页测试能力验证 iframe、缩放与交互。
- 可启动本地静态服务器进行非 `file://` 场景验证。
- Manifest 中的安全区域和预览尺寸必须根据最终框架渲染结果测量。
- 交互 Demo 测试需要至少两个可导航页面和一个返回场景。
- 旧框架兼容测试需要保留一个 `.phone-frame` 或同类旧结构样例。
- 实施前必须确认当前工作区中被删除、未跟踪和已修改文件的所有权与范围。

# 验收标准

1. 不完整需求调用 `brainstorming-solo`，完整 PRD 调用 `grill-me`，原确认门禁保持有效。
2. UI Skill 发现覆盖会话清单、本地目录、重名、junction、无效、不可调用和零结果场景。
3. 所有有效 UI 相关 Skill 均展示，用户只能选择一个主 Skill；无 Skill 分支从参考产品/网站开始逐项提问。
4. 两个特殊 UI Skill 的固定链接正确显示，且不会未经允许自动打开。
5. Manifest 可解析、ID 唯一、端口映射正确，框架文件、逻辑画布、预览尺寸、安全区域和协议与源码一致。
6. `design-direction.html` 使用独立首页预览和选中框架，无重复系统 UI。
7. `index.html`、正式页面和项目配置使用相对路径，按设备类型采用已确认的默认列数。
8. 功能三左侧到右侧、右侧到左侧、返回历史、错误处理和页面白名单均正常。
9. 功能三新框架模式与旧框架兼容模式均通过。
10. 功能四能够识别配置缺失、配置冲突、旧框架、重复状态栏、尺寸错误和缺失框架，并保持 Level 1/2/3 门禁。
11. 设计方向、预览、静态页面、交互 Demo、框架迁移和项目配置变更均按规则记录 EditLog。
12. 本地 HTML、静态服务器和移动目录后的原型均可加载；双层 iframe 消息仍然有效。
13. 相关评估规则覆盖路由、UI Skill 发现、端口映射、Manifest 失败、iframe 通信、旧原型兼容和日志。
14. 文档不存在冲突尺寸、旧主框架类依赖或未经确认的安全区域事实。
15. Git diff 中不存在与批准 Spec 无关的改动。

# 风险与回退注意

- Manifest 与框架源码漂移：先完成数据真源和一致性验证，再修改下游文档；发现漂移时停止下游工作。
- 框架视觉或尺寸回归：保留修改前后渲染证据；只回退本次产生的框架改动，不触碰用户其他文件。
- 双层 iframe 通信失败：先验证最小两页面消息中继，再接入完整 Demo；失败时不得删除旧兼容逻辑。
- `file://` 的 origin 为 `null`：联合校验 `event.source`、channel、协议版本和页面白名单，不只依赖 origin。
- UI Skill 目录不可访问：按降级顺序继续，不伪造安装结果。
- 用户选择不可调用 Skill：提示并重新选择，不自动替换。
- 旧原型迁移导致视觉变化：功能四按 Level 1/2/3 分级处理，Level 3 必须重新确认。
- 当前工作区脏状态：不得用全局回退命令；必要时通过逐文件补丁撤销仅由本次实施产生的内容。
- 评估文件处于删除状态：不自行恢复；可以新增独立验证材料或等待用户确认后再更新原评估文件。

# 完成定义（Definition of Done）

只有在以下条件同时满足时，后续 Agent 才能将工作视为完成：

- 批准 Spec 范围内的入口、功能文档、共享规范、框架库、README 和相关评估规则已一致更新；
- Manifest、五个框架源码及框架 README 通过一致性检查；
- UI Skill 发现、无 Skill 分支和特殊链接规则可按文档执行；
- 功能一、三、四共用新框架体系，功能二和功能三/四既有业务流程未被改动；
- 新框架双层 iframe 通信和旧框架兼容均通过代表性测试；
- 本地文件、静态服务器和目录迁移验证通过；
- EditLog 规则覆盖新增文件和框架配置；
- 没有未完成标记、关键占位符或未说明失败；
- Git diff 仅包含本次批准范围内改动，用户已有无关修改保持原状；
- 完成说明列出修改文件、验证结果、已知限制和未解决事项；若仍有必需工作未完成，不得声明完成。
