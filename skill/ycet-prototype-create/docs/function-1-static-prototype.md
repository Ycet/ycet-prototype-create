# 功能一：从产品需求到高保真静态原型页面

## 目标

根据产品想法、零散需求或 PRD，生成高保真静态原型页面，包括：

- `prototype/docs/Spec.md`
- `prototype/design-direction.html`
- `prototype/index.html`
- `prototype/pages/*.html`
- `prototype/docs/EditLog.md`

凡涉及原型 HTML 或图片承载页面写入/修改，必须按 `shared-editlog-rules.md` 记录。

## 阶段一：产品需求完善

### 输入判断

先分析用户输入属于哪类：

| 输入类型 | 必须动作 |
| --- | --- |
| 一句产品想法、零散需求、口述功能点、未成体系需求文档 | 必须读取并使用 `superpowers:brainstorming` |
| 结构化 PRD、需求说明书、功能清单文档、飞书/Markdown/Word 等较完整材料 | 必须读取并使用 `grill-me` |
| 无法判断是否为完整 PRD | 按“不完整需求”处理，使用 `superpowers:brainstorming` |

### 需求完整度审计

在追问前先输出缺口清单。后台固定检查以下维度：

- 产品端口；
- 产品背景；
- 产品定位；
- 功能清单；
- 核心功能；
- 功能需求六维：功能说明、交互逻辑、页面元素、业务流程、边界条件、异常处理；
- 补充问题。

审计后每轮只问一个最高优先级问题，并提供推荐选项。

### `Spec.md` 生成门槛

只有满足以下条件，才允许生成 `prototype/docs/Spec.md`：

1. 产品端口已确定。
2. 页面清单已能列出。
3. 每个核心功能至少覆盖：功能说明、页面元素、业务流程、异常处理。
4. 核心页面之间的流转关系已能描述。
5. 仍不确定的内容必须写入 `Spec.md` 的“待确认事项”，不得偷偷补完。

生成后必须向用户展示并请求确认；用户未确认，不得进入阶段二。

### `Spec.md` 内容要求

`Spec.md` 目的是指导高保真静态原型制作，重点记录：

- 页面清单；
- 各页面核心元素 / 组件；
- 页面内交互逻辑；
- 页面间交互流程；
- 异常处理逻辑；
- 业务规则；
- 边界条件；
- 待确认事项。

产品背景、目标用户、非功能需求、接口定义等只需简要概括。

## 阶段二：UI 设计方向确定

阶段开始时先问用户是否指定 UI 设计相关 skill，例如 `ui-ux-pro-max`、`frontend-design`。

- 若用户指定 skill：必须读取并按该 skill 生成候选方向。
- 若用户未指定：基于已确认的 `Spec.md`，提出 2-3 套 UI 方向。

每套方向必须包含：

- 适用场景；
- 视觉关键词；
- 主色建议；
- 组件气质；
- 参考产品类型；
- 风险点。

用户确认一个方向后，才生成 `prototype/design-direction.html`。

### `design-direction.html` 要求

文件用于预览 UI 设计规范，至少包含：

- 色彩方案；
- 字体层级；
- 按钮样式；
- 反馈组件；
- 设备框架预览；
- 首页 UI 效果展示；
- 必要的补充组件示例。

生成后必须请求用户确认；未确认不得进入阶段三。

## 阶段三：静态原型生成

写任何 HTML 前，必须先在会话窗口输出简短实现计划并请求用户确认，不需要生成单独文档。

实现计划必须包含：

- 页面文件清单：每个页面对应 `prototype/pages/*.html` 文件名；
- 页面与功能映射；
- 框架类型与设备框架尺寸；
- 静态原型范围：只做页面内交互，不做跨页面跳转；
- 共享规范读取项：生成前必须读取 `shared-prototype-standards.md` 与 `shared-editlog-rules.md`；
- 生成后验证项：iframe 路径、页面尺寸、无横向溢出、页面内交互、图片加载、EditLog 记录。

用户确认计划后，读取共享规范并生成文件。

## 完成标准

- 所有文件符合 `shared-prototype-standards.md`。
- `prototype/docs/EditLog.md` 至少记录“生成静态原型页面”。
- 完成后说明生成文件、查看方式、下一步可使用功能三生成可交互 demo。
